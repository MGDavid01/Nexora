b. Introducción

Problema que resuelve

Nexora es una aplicación web de intermediación de servicios de soporte técnico. El problema que ataca es la dispersión del ciclo de asistencia: quien necesita ayuda y quien puede prestarla no comparten un mismo expediente de solicitud, cotización, ejecución, informe, calificación e historial. El producto centraliza esos actos en un solo entorno, con acceso por rol (cliente, empresa, negocio, técnico y administrador de plataforma) y con registro de lo atendido para consulta, recontratación y análisis.

No es una tienda de refacciones, ni un sistema contable del proveedor, ni un sustituto del técnico en sitio. El solicitante es persona o empresa; no hay auto-registro: las altas las da el administrador. Un perfil cliente tiene un solo usuario; una empresa tiene administrativos y técnicos; un negocio tiene un único usuario con función de administrativo de campo.

Objetivo general

Operar, en esta entrega de cuatrimestre, un producto web completo de intermediación: publicar y gestionar solicitudes, cotizar con plazo de 24 horas sin reservar la solicitud, elegir una cotización, seguir el servicio hasta el cierre con informe y calificación mutua, sancionar con un catálogo fijo de marcas, auditar actos administrativos y simular ingresos (comisión por cierre y N % de alquiler de ESP32), sin pasarela de pagos.

Alcance del agente dentro del sistema

En el código, «el agente» no es un chatbot de la interfaz web. Es el canal de voz del aparato de campo (actividades N3 y N4): un ESP32-S3 alquilado a un perfil cliente o proveedor. El administrador da de alta el dispositivo en un pool, muestra una clave de un solo uso y lo asigna. El firmware (o el cliente local firmware/simulador.py) autoriza con identificador y clave, envía latido y datos, consulta comandos y llama POST /api/v1/aparato/voz.

El flujo de voz implementado es: texto o audio → transcripción (STT) → respuesta del agente local → síntesis (TTS) → comando pendiente de tipo «hablar». En este entorno las URLs de STT y TTS están vacías, así que transcripción y voz usan mocks. El agente de software tampoco llama a un modelo externo: si el aparato está asignado a un cliente, orienta a publicar una solicitud (título, descripción, categoría y ubicación); si está asignado a un proveedor, orienta a dictar el informe de servicio. Si está en el pool, el canal de voz responde 409. La web funciona igual sin el aparato. La pantalla /proveedor/captura lo declara: no hay conversación embebida, solo un aviso de que la captura ocurre en el dispositivo autorizado.

c. Desarrollo

1. Arquitectura

La arquitectura es de tres capas locales más adaptadores opcionales. El frontend (React 19, Vite, TypeScript) se sirve en el puerto 5173 y proxifica /api y /salud hacia el backend. El backend es FastAPI (app.main:app, título Nexora 0.1.0) con JWT para usuarios web y JWT distinto para aparatos. PostgreSQL 16 guarda usuarios, perfiles, solicitudes, cotizaciones, servicios, historial, marcas, reclamaciones, tarifas, alquiler de ESP32, auditoría, datos y comandos del aparato. Alembic aplica el esquema; python -m app.seed carga cuentas de demo de forma idempotente.

Los servicios externos viven en backend/app/adaptadores/. Correo Google (SMTP): avisos y recuperación de contraseña; sin usuario y contraseña el envío se omite y el acto de negocio sigue. Cloudinary: evidencias y fotos; en base de datos solo la referencia; sin credencial la subida se omite. OpenStreetMap: Nominatim para geocodificar (máximo una petición por segundo) y teselas Leaflet en el mercado del proveedor. Avisos: hooks de marca, denegación, vencimiento a 24 h y cancelación, que pueden disparar correo. El aparato tiene router /api/v1/aparato, servicio de autorización, datos, comandos y canal_voz, firmware en C (esqueleto ESP-IDF) y simulador Python.

4. Interfaz del agente

No existe una interfaz conversacional tipo chat en React. La interacción real más cercana es la concatenación de (1) la pantalla de dispositivos del administrador, (2) el aviso de /proveedor/captura, (3) Swagger de /api/v1/aparato y (4) el cliente de prueba firmware/simulador.py.

  • El administrador da de alta el ESP32 en el pool y copia la clave (una sola vez).
  • Asigna el aparato a un perfil cliente o proveedor (alquiler, no suscripción).
  • El aparato (o el simulador) llama POST /aparato/autorizar y recibe un JWT de aparato.
  • Latido y datos actualizan visto_en; el admin ve «en línea» si cabe en 90 s.
  • POST /aparato/voz con texto (o audio) produce transcripción, respuesta del agente mock y encola un comando hablar.
  • GET /aparato/comandos entrega el payload para la bocina; el ack lo marca acked.

Respuestas observadas con el aparato NEX-DOC-VOZ-02 asignado a Daniela Camacho y el texto «el equipo no enciende»: transcripcion igual al texto, stt = texto, tts = mock, agente = mock_cliente, audio_b64 vacío, y respuesta que indica publicar una solicitud con título, descripción, categoría y ubicación. El comando pendiente es tipo hablar. No se atribuyen capacidades de un modelo externo.

5. Vista global del proyecto

El dashboard de administrador y sus módulos (Usuarios, Trabajos, Reportes, Ingresos, Dispositivos, Auditoría) son la vista global: el equipo ve el padrón, el expediente de cada caso, las métricas, la comisión simulada, el pool de ESP32 y el log. Eso refleja el trabajo colaborativo de bases/equipo: el frontend no se toca desde backend; Héctor cubre cliente/empresa/negocio; David, administración y adaptadores; Andrés, seed, esquema y aparato. El administrador de plataforma da de alta cuentas y asigna aparatos; el resto opera sobre el seed y /api/v1.

Un integrante puede revisar Swagger mientras otro usa la web, porque ambos hablan con el mismo PostgreSQL. Los reportes no sustituyen al historial; la auditoría no sustituye a Trabajos.
